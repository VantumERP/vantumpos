# SW-16 — Popis — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the annual and nivelacija popis as a two-phase blind count with two statutory signature events, the required separate lists, a structured izveštaj, a computed deadline engine, and a write-lock on posting.

**Architecture:** A state machine (`draft → counting → counted_signed → computed → computed_signed → posted`) is the whole module. Phase B data is unreachable from Phase A **at the query layer**, not merely hidden in the UI — that is what makes PoP čl. 8 st. 5 a property of the system rather than a UI convention. Deadlines are computed from the FS filing rule, never tabulated.

**Tech Stack:** Rust (rusqlite, serde) + Tauri v2 commands; React 19 + TypeScript + shadcn/ui + vitest; bun.

## Global Constraints

- **Money is integer minor units; quantities milli-units.** Never floating point.
- **Timestamps RFC3339 passed as a `now: &str` param.** Never `datetime('now')` in decision code, and **never a wall clock in the deadline engine**.
- **Serbian Latin diacritics** in every operator string; Serbian quotes open `„` and close `“`.
- **Migrations APPEND-ONLY.** Read the current count from `db/mod.rs` first; this is the next free version.
- **NO fine figure outside `legal.rs`**; new notices go into **both** guard lists with the count bumped.
- **No book quantity may be readable during Phase A** — enforced in the query layer and asserted by test.
- **There is no obrazac for the popisna lista.** Do **not** carry over the SW-9c KEP print-fidelity constraints. **But the izveštaj content IS prescribed** (PoP čl. 13 st. 1).
- **Never boot the app.** Verify only via the gates.

**Gates:** the standard six.

- [x] **Step 1: Write the failing tests** — the tables exist; the status enum is a closed CHECK; a `popis_signatures` row has no `updated_at`; `knjigovodstvena_kolicina_milli` is nullable; **a survival test applying `MIGRATIONS[..N]` to a raw Connection, seeding, `drop(conn)`, then `Db::new`** — mirror commit `270796c`.
- [x] **Steps 2–5.** Landed as migration **v20** (`popis_stores_blind_count_and_posting_lock`). Beyond the four tables, the migration enforces two module invariants in the engine rather than leaving them to a later layer, because migrations are append-only and these two cannot be added later without a second migration the plan does not budget for: **the čl. 8 st. 5 blind count is a write guard** (a book quantity is refused while the session is in `draft`/`counting` **and while no `faza = 'a'` signature exists for it**, so during a count none exists for any query, export or backup to leak — req. 29), and **posting write-locks the session, its lines, its commission and any new signature** (req. 41), with `popis_signatures` immutable from the moment each signature is taken. The guard is anchored on the potpis rather than on `status` alone because `status` is a claim any `UPDATE` can make — a session flipped or born into `counted_signed` with no signature behind it is refused the book data. **Contract for Task 4:** `popis_sign_phase_a` must write the signature row *before* it populates any `knjigovodstvena_kolicina_milli` (the statutory order anyway), and `popis_post` must write everything else *before* flipping to `posted`, since that flip is the last permitted write. No popis table may be written with `INSERT OR REPLACE`/upsert: `REPLACE` deletes and re-inserts, so no `BEFORE UPDATE` lock fires. `DELETE` stays open on all four tables for the req. 42 retention purge, as v18 and v19 each reasoned. Deviations: identifiers and stored enum values are ASCII-folded per the schema-wide convention (`uskladjivanje_potvrdjeno_at`, `ostecena`, `potrazivanja`), and `popis_commission.uloga` is a closed enum (`predsednik | clan | jedno_lice`) rather than free text, so the čl. 6 st. 1 single-person popis is expressible instead of implied.

### Task 3: The deadline engine (req. 38)

`izvestaj_due(vrsta, datum_popisa, fs_filing_deadline) -> String`. **Compute `filing − 60 days` for the annual mode; `datum_popisa + 30 days` for nivelacija. Do not hardcode dates.**

- [x] **Step 1: Write the failing tests** — FY2026 → 30 January 2027; FY2027 → 31 January 2028 (**leap year — this is the case a hardcoded table gets wrong**); FY2028 → 30 January 2029; nivelacija → +30 days from the count; the function takes the filing deadline as a parameter so a statutory change is a config edit, not a code change.
- [x] **Steps 2–5.** Landed in `src-tauri/src/popis.rs` alongside the state machine. Twelve tests — nine at first, three more from the review fixes below — each verified load-bearing by mutation: hardcoding the annual answer as „30 January of the filing year“ fails **only** the FY2027 row (`left: 2028-01-30, right: 2028-01-31`), which is exactly the case the plan named. Beyond the plan's four named behaviours: the annual rok does not move when the count date does (čl. 13 st. 2 anchors it on the rok za dostavljanje, and an engine anchored on `datum_popisa` would agree with the FY tests every time the popis fell on 31 December — which for the annual popis is nearly always); the nivelacija limb does not read the filing deadline at all (the dangerous fall-through direction: it would give an in-year popis a rok months later than the 30 days čl. 13 st. 2 allows, and the shop would file late believing the app); the nivelacija cases cross a month end, a year end and a 29 February, so the 30 are calendar days and not „a month“ — the same 5 February is 6 March in 2028 and 7 March in 2027; every unreadable date is refused rather than repaired, including the two near-misses a lenient parser eats (`2027-3-31` and an RFC3339 stamp); and `PopisVrsta` is pinned to the v20 `vrsta` CHECK and to its own IPC wire form, for the reason the status test gives — here the drift would silently swap two **different statutory roks**. **One test asserts the source, not an answer:** design §7 t. 5 („no hardcoded deadline dates“) and the standing „never a wall clock in the deadline engine“ are properties no behavioural test can see — it cannot tell a computed 30 January 2027 from a hardcoded one, nor a rok derived from its arguments from one that read the clock and happened to agree today — so the non-test half of the module is scanned for a `gggg-MM-dd` literal and for every spelling of a wall-clock read: `utc_now`/`now_utc`/`Utc::now`/`Local::now`/`now_local`/`SystemTime::now`/`datetime('now')` (both limbs verified by mutation). **Review fix:** the first of those was missing. `crate::clock::utc_now` is this repository's own canonical reader (47 call sites) and is **not** matched by the substring `now_utc` — neither string contains the other — so the guard was hollow against the one way a clock would actually arrive here; injecting `let _clock = crate::clock::utc_now();` into `izvestaj_due` left all 18 tests green. A second test now pins the scanned list to what `src/clock.rs` actually exports, so a future `pub fn` there fails until the engine's guard has learned to scan for it (both verified by mutation). **Deviations from the plan's stated interface, both about what the function does when it cannot answer:** (1) it returns `Result<String, AppError>` rather than `String` — it parses two dates it does not own (one typed by the shop, one from configuration), and with a bare `String` an unreadable one has nowhere to go but a panic or an invented rok; a rok this module invents is one the owner files on, and the čl. 58 prekršaj attaches to the popis. Codes: `popis_rok_neispravan_datum`, `popis_rok_predaje_fi_nepoznat`, `popis_rok_van_kalendara`. **Review fix:** the third code had no test and only half a refusal. The overflow is genuinely reachable (a nivelacija counted on `9999-12-31`) and was already refused; the underflow was not — `{:04}` renders year −1 as `-001`, so a rok computed back from a year-0000 filing deadline came back as `Ok("-001-12-03")`, a string neither `gggg-MM-dd` nor storable in any v20 date column, returned as a **success**. `iso_datum` now yields `Option<String>` and refuses anything before year 1 through that same code, and a test asserts both directions. (2) `fs_filing_deadline` is `Option<&str>` rather than `&str` — čl. 13 st. 2's second limb does not read a filing deadline, so requiring one would make every nivelacija caller fabricate a date that is then ignored; the annual limb refuses `None` by name instead. Addition: `PopisVrsta` (`godisnji | nivelacioni`), because Task 3's own signature names a `vrsta` and no enum existed; modelled on `PopisStatus`, ASCII-folded like the column. **Contract for Tasks 6 and 7:** čl. 14 st. 2 gives the odluka o usvajanju the rok *„iz člana 13. став 2“* — it is the same date, so it gets no second function and no second deadline field; the izveštaj and the odluka are surfaced from this one answer (req. 38). Task 7 calls it with `PopisVrsta::Nivelacioni` and `None`. Nothing here reads a clock or a setting: the filing deadline is a parameter because ZoRač čl. 44 st. 1 sets 31 March *„osim ako posebnim zakonom nije drukčije uređeno“*, so the rok is not this module's to own — but that also means **no caller yet supplies it**, and Task 4 or 6 owes it a configured source rather than a constant.

- [x] **Steps 2–5.** Landed as `src-tauri/src/commands/popis.rs` (18 tests) plus one five-line extraction in `popis.rs`. Every named behaviour has a real assertion and **each was verified load-bearing by mutation** — fourteen mutations run, each caught, and the two that were *not* caught are recorded below rather than papered over. The čl. 8 st. 5 property is enforced in **two** places for the two different things it forbids: the write side refuses a payload carrying a book quantity with `popis_knjigovodstvo_pre_potpisa` (refused, never dropped — a client that silently had the field discarded would believe it had stored book data), and the read side takes Task 2's contract literally. `read_lines` is **two statements rather than one and a filter**: while the data is withheld the query does not name `knjigovodstvena_kolicina_milli` and does not name `inventory_balances` or `inventory_movements` either, so there is no value in the row for a refactor, a log line or a debug print to spill. The test asserts it on the **whole serialized response** — a product is seeded with a distinctive perpetual balance and that number must appear nowhere while the popis is counting, and must appear once the potpis is taken, so the first half cannot pass vacuously. Mutation-checked with the exact defect Task 2 warned about: adding an „očekivano“ column to the blind query by joining `inventory_balances` fails **only** that test, with the rest of the suite green. The signature step writes in the statutory order — potpis, then state, then book quantities — and the order is behaviourally proven rather than commented: reversing it fails five tests, because the v20 guard aborts a book quantity written before its potpis. **Deviations and additions.** (1) `popis.rs` gained `posting_lock(status)`, extracted from `advance`'s existing `Posted` early-return with no behaviour change, because the command layer refuses edits that are not transitions at all — a line write, a komisija row — and a second hand-written copy of that sentence would have been free to drift from the engine's and from the v20 trigger's. (2) Beyond the plan's three named commands the module ships `popis_list`, `popis_get`, `popis_save_line`, `popis_start_count`, `popis_compute` and `popis_sign_phase_b`: the machine has five arrows, and Task 2's contract puts the čl. 8 st. 5 enforcement in the **query layer**, which has to exist to be enforced. The warning names the person, cites čl. 5 st. 1, says the čl. 6 st. 1–2 shodna primena **is not settled** (§6 R-5) and says the popis was not stopped; the test asserts all four, because a warning that read like a refusal would be an operator string promising behaviour this module does not implement. Without this a signed potpis could attest to a state that no longer existed. (5) The book quantity is read from `inventory_balances` joined on `products.sku = popis_lines.sifra`, at the moment the potpis is taken — the earliest moment čl. 8 st. 5 permits reading it at all. A šifra that resolves to nothing keeps its NULL rather than a zero: the gotovina and potraživanja liste have no perpetual record behind them and a fabricated zero would report a manjak the shop does not have. Čl. 8 st. 4 is what the commission is *handed* (nomenklaturni broj, naziv, vrsta, jedinica mere) and čl. 9 st. 1 t. 1 is what it *signs* (the count with its bliži opis), so all of it is now pinned: a Phase B write that moves any of those fields is **refused** by name (`popis_stvarno_stanje_potpisano`, naming which field moved) rather than ignored, one test case per field plus a positive control that the obračun can still price the stavka. The two čl. 8 st. 4 fields the snapshot did not cover (`vrsta`, `jedinica_mere`) were added to it, so the set the hash attests to and the set the obračun may not move are **one list** — asserted by its own test, all seven fields, mutation-verified in both directions. (b) **Req. 34 was not implemented and not declared.** `perpetual_odluka_ref` was stored as unvalidated free text under a doc comment claiming it pointed at „the completed, adopted and posted in-year popis it rests on“ — a guarantee nothing gave. Three tests: refused with nothing behind it, refused when the in-year popis only reached `counting`, refused when the posted popis is from another year, accepted once one is posted. **Declared deviation:** čl. 9 st. 2's *usvojen* limb — the čl. 14 st. 2 odluka o usvajanju — is **not** checked, because no schema records that decision yet. **Task 6 owns the odluka o usvajanju and owes this gate its second limb.** The field's doc comment now states exactly what is checked and what is not.
